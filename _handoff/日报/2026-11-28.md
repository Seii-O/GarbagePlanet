## 补充（14:39 起）：BackpackCapAt 越界崩溃修复

### 现象

- 进 Play 后 `WhiteboxCanvasHud.Update → Refresh` 每帧抛 `IndexOutOfRangeException`，栈指向 `WhiteboxConfig.BackpackCapAt`（`WhiteboxConfig.cs:201`），IL 偏移 `0x7b`。`Editor.log` 第 4380 行，出现在 14:37:53「启动完成」之后；日志内 `error CS` 为 0 条，即程序集是新的，不是编译失败留下的旧版本。

### 原因

- 上一版 `BackpackCapAt` 用「**一个 `capCache` 数组反复复用**」做单级缓存：每换一个等级就把同一份数组的内容重写一遍。这种共享可变缓存一旦拿到的不是长度 4 的数组（旧对象残留 / 缓存被其他路径改写），第 201 行 `capCache[i]` 就必然越界。根因是**缓存形态本身不安全**，不是某个调用点算错了等级。

### 修法

- `Data/WhiteboxConfig.cs`：
  - 删掉 `capCache` / `capCacheLevel` 单数组缓存，改为 `int[][] capRows`——**按等级分行缓存**，每个等级各自一份独立数组，调用方持有引用后不会被下一次别的等级的计算改写。
  - 新增 `const int CapSlots = 4` 与 `static int AtSlot(int[], int slot, int fallback)`：所有源数组取值（`backpackCap` / `backpackCapPerLevel` / `CapPerLevelDefault`）一律走带 null 与长度检查的读取，下标越界返回兜底值，不再直接索引。
  - 行下标再做一次兜底：`idx = lv-1` 先夹到 `0`，再夹到 `capRows.Length-1`；取行时校验 `row.Length == CapSlots`，不符则重算。
  - `OnValidate` 的缓存失效由 `capCacheLevel = -1` 改为 `capRows = null`。
  - 新增 `#if UNITY_EDITOR` 一次性告警：`backpackCap` 长度不是 4 时打 `LogWarning`，便于在 Inspector 里发现配置问题（不影响运行）。
- `UI/WhiteboxCanvasHud.cs`：>80% 呼吸边框那段，循环上界由写死的 `4` 改为同时受 `bagCaps.Length` 与 `s.bag.Length` 约束的 `slots`，任一数组变短只少算不抛异常。

### 补充修复（15:20）：狗「叼一次垃圾就瞬移一次」

- **现象**：5 m 版进 Play 后，狗每叼到一件垃圾，位置会向前猛冲约一个身位（≈0.87 m），观感像瞬移。

- **为什么用累加器**：补刷是「捡一件补一件」，每批只有 1 件，逐件掷骰子会退化成纯随机（可能连出 5 个大件）；`active.Count % N` 又会被 `Recycle` 改动的计数打乱节奏。累加器能表达 0.03 / 0.06 这类 1/N 以外的比值，长周期比例精确。
- **渐进性**：已经躺在地表的大件不受升级影响，只有新补进来的按新等级比例生成 —— 升级时不会全图换血，而是「世界慢慢变得更多大件」。
- **已知偏差**：电子类没有大型外观（大件只有塑料/金属/有机三种），抽中名额会经 `PickPrefabForCategory` 回落成小件，所以实际值约为配置 ×0.83（补刷端）。
- **数量参考（3000 件铺场）**：Lv.1 约 90 个、Lv.2 约 180、Lv.3 约 300、Lv.4 约 480、Lv.5 约 660；改前固定约 428 个。
- **待验证**：① Lv.1 开局视野里能否找到大件、任务第 3 步「拆 1 个大件」是否卡住；② 升级到 Lv.4 后补刷的大件是否明显变多；③ 电子类是否仍正常出小件、没有空刷。

## 补充修复（16:10）· Lv.4 大件依然很少

**现象**：用户实测「Lv.4 大件看起来很少」，与配置的 16% 对不上。

**根因**：`Assets/Data/WhiteboxConfig.asset` 里**根本没有 `largeSpawnRatio` 这个键**。Unity 不会把新增的 SerializeField 自动写回已存在的资产，运行时读出来是空数组；旧访问器 `At(arr, level, 0.04f)` 遇到空数组直接返回标量兜底，于是**所有等级都变成 4%**——Lv.1 的 3% 和 4% 几乎一样，所以直到 Lv.4 才暴露。同理 `OnValidate` 里的 `Ensure(ref largeSpawnRatio, ..., 0.04f)` 也会把空表填成 5 个 4%。

**修法**：
- `WhiteboxConfig` 新增 `static readonly float[] LargeSpawnRatioCurve = {0.03,0.06,0.10,0.16,0.22}`；`LargeSpawnRatioAt` 改为「数组缺项按曲线逐级兜底」，不再是所有等级同一个值。
- 新增 `[HideInInspector] int spawnRatioVersion` + `MigrateDefaults()`：启动时检测到版本 0 就按曲线补齐并置 1，编辑器下 `SetDirty` 让资产真正写回这些键。`WhiteboxGame.Awake` 第一行调用。
- `OnValidate` 的补齐逻辑改为按曲线填，不再统一填 4%。
- `TrashSpawner` 的 `largeDebt` 累加器换成 `largeOnSurface` 计数 + 缺口判定（`RollLarge` 比较「该有的大件数」与「已有的大件数」）：升级后缺口一出现，新补的每一件都先补大件，比例自动收敛；电子类回落吃掉的名额也会被下一件自动补回，实际比例不再打 0.83 折。
- `TrashSpawner.Init` 末尾加一行诊断日志：`[WhiteboxTrash] 人物 Lv.X · 大件目标占比 Y% · 目标件数 N · 实际铺场大件 M/总数`。

**遗留**：升级发生在**同一次游戏里**时，地表存量不会立刻重排（按 1:1 补位，要把 400 多件缺口补完才追上），观感上「升级后新冒出来的都是大件」但总量变化慢。若要「升级瞬间就换血」，需要加一次「在玩家背半球静默把部分小件替换成大件」的收敛，已告知用户待拍板。

## 追加（16:20）· 背半球静默替换

用户拍板做背半球替换，其余不动。

- **规则**：`TrashSpawner.TickLargeCatchUp()` 每秒结算一次配额，把与玩家角距 > `largeCatchUpMinAngle`（默认 **60°**）的小件换成同类大件，速率 `largeCatchUpPerSecond`（默认 **6 件/秒**）。
- **为什么 60° 一定看不见**：玩家眼高约 1.6 m、星球半径 8 m，地平线的中心角 `acos(R/(R+h)) ≈ 33.6°`，即 34° 之外就在地平线以下，60° 有充分余量。`OnValidate` 把下限钳在 35°，防止有人调小到看得见的位置。
- **实现要点**：倒序遍历 `active`（`Recycle` 会摘元素）；电子类跳过（没有大型外观）；跳过玩家准星当前目标；用 `Recycle` 而不是 `Despawn`（不增加 `clearedTrash`）；`Spawn` 原地同类替换，不播冒出动画；`active` 数量与类别分布都不变，只是体型换了。
- **与既有逻辑的关系**：`RollLarge` 仍然按缺口判定，两条路一起收敛；缺口 ≤ 0 时静默替换直接停手，不会反向把大件改小。
- **手感**：Lv.1→Lv.4 缺口约 390 件，按 6 件/秒约 1 分钟追平；期间玩家看到的正面半球不变，走到背面时已是新比例。
- **未验证**：编译、Play 观感、低端机上 6 件/秒的 Instantiate 是否掉帧。
